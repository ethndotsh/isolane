---
title: Tune warm starts
description: Size a program's instance pool, keep instances and spare workers ready, and set what each worker caches, then measure the result.
---

Before a call runs, it can wait for a [worker](/concepts/architecture) to
start, an isolate to be created, and a program's modules to load. The
`instances` option on each program and three runtime options, `spares`,
`spareIsolates`, and `caches`, shorten each of those waits.

## Measure first

Each program instance's load is reported to `onProgramLoad`:

```js
const runtime = new Runtime({
  hooks: {
    onProgramLoad: ({ tenant, program, durationMs, modules, error }) => {
      console.log(tenant, program, durationMs.toFixed(1), modules, error?.code);
    },
  },
});
```

```text
acme 1 11.2 { compiled: 1, cached: 0, rejected: 0 }
acme 1 3.5 { compiled: 1, cached: 0, rejected: 0 }
acme 1 2.7 { compiled: 1, cached: 1, rejected: 0 }
```

The first line is the program's first instance, which `tenant.load()`
waits for. Later instances find the program's files already in the
worker, and once the first instance has finished, they also find V8 code
caches of its modules: `cached` counts the modules compiled from one.
`program.usage()` shows the pool as it is now: `instances`, `busy`, and
`queued`.

## Size the pool

```js
const program = await tenant.load(source, {
  instances: { min: 2, max: 8, idleMs: 60_000, queueMs: 2_000, queue: 100 },
});
```

By default a program keeps no idle instances (`min: 0`), runs at most 4
(`max`), closes an idle one after 30 s (`idleMs`), and lets a call wait 10
s (`queueMs`) behind at most 1,000 others (`queue`) before it fails with
`ERR_LIMIT`. [Program](/reference/program#instances) lists every field and
its range.

Set `min` to the number of calls you expect at once in quiet periods, so
the first request after a lull does not wait for a load. Each instance is
an isolate and counts toward the tenant's `isolates` limit (100 by
default), and its heap counts toward the worker's `workerMemoryBytes`, so
`max` across a tenant's programs should stay below both.

A short `queueMs` makes callers fail fast with a status they can retry,
instead of waiting behind a backlog. `reuse: false` loads a new instance
for every call, which suits code whose end users must not share module
state; the code cache keeps each of those loads short.

## Run several calls per instance

```js
await tenant.load(source, { instances: { max: 2, concurrency: 8 } });
```

Handlers that spend most of their time waiting on host functions or
`fetch` can share an instance: up to `concurrency` calls run on its event
loop at once, and new instances are loaded only when every instance is
full. The calls share the instance's per-eval budgets (`cpuMs`,
`hostCalls`, `logBytes`) and its event loop.

With `concurrency` above 1, one call stuck in a synchronous loop holds up
every call in its instance, so one stuck call can fail them all and retire
the instance ([Programs](/concepts/programs#concurrency) explains why).
Keep `concurrency` at 1 for handlers that may compute for a long time.

## Keep workers and isolates ready

A tenant's first eval starts its worker process, which takes tens of
milliseconds. `spares` keeps that many workers started ahead of time; a new
tenant claims one whole, and it serves only that tenant from then on.

```js
const runtime = new Runtime({ spares: 2, spareIsolates: 2 });
```

`spareIsolates` (0 to 8) has each tenant's worker create that many web
isolates in advance, which is most of a fresh web isolate's start. Spares
are kept for each of the four heap sizes (`limits.heapBytes`) the worker
used most recently, so a worker holds at most `spareIsolates` × 4. An
isolate with a `random.seed`, or with `web: false`, cannot use a spare;
[Caches](/concepts/caches#spare-isolates) explains why.

Measured on a macOS development build, a fresh web run took 0.25 ms with a
spare ready instead of 1.5 ms, and a later program instance 2.4 ms instead
of 3.3 ms. Each spare worker uses about 15 MB while idle, and each spare
isolate about 3 MB, which is why both default to 0.

## Set what each worker caches

Each tenant's worker keeps what later instances of a program need. The
`caches` option sets the budget for each kind, in bytes:

```js
const runtime = new Runtime({
  caches: { fileBytes: 128 << 20, codeBytes: 128 << 20, wasmBytes: 0 },
});
```

`fileBytes` keeps programs' files (64 MiB by default), `codeBytes` V8 code
caches of their modules (64 MiB), and `wasmBytes` compiled WebAssembly (32
MiB); [Configuration](/reference/configuration#caches) has the details. 0
keeps nothing of that kind. What a worker keeps counts against its
`workerMemoryBytes`, so raise that limit with the budgets if your programs
are large. The budgets apply to every tenant's worker, and a recycled
worker starts empty.

Measured on a macOS development build with a 747 KB bundle and
`reuse: false`, the first instance loaded in about 16 ms and each later one
in about 3 ms. With neither the files nor the code cache kept, each load
took about 13 ms.

## If later instances are not faster

Check `modules` in `onProgramLoad`. `cached: 0` on every load after the
first means the code cache is not used: `codeBytes` may be 0, or the
program may be loaded again with different files or `ts`, `jsx`, or
`define` options, which changes the cache key. `rejected` above 0 means V8
refused a cache, for example after the worker binary changed; isolane
compiles from source and makes a new one. A worker that is recycled
(`workerLifetimeMs`, `workerEvals`) or that exits after `idleMs` with
nothing running also starts with empty caches.
